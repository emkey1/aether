# Proposal: a map type, `Map[Text, T]` (D68, accepted 2026-10-20)

Status: accepted by the owner as an immediate goal; supersedes D47 (no map type).

## Why now

- Models reach for dictionaries constantly: word counts, grouping by key, lookups by name. Keyed
  accumulation over JSON/TOON data is Aether's niche.
- D47's taught substitute, a record of parallel `keys`/`values` arrays, works but is verbose, and it invites
  silent index mismatches.
- D47's objection was a `map_get_int` / `map_get_text` / … builtin family per value type, a second, competing
  name set. A container in the type system, like `T[]`, has no such family: the value type rides in the type.

## Surface

```aether
let ages: Map[Text, Int] = {"ann": 31, "bob": 27};
let empty: Map[Text, Real] = {};          // `{}` needs a declared type

ages["cid"] = 40;                          // insert or overwrite
let a: Int = ages["ann"];                  // read; a missing key is a runtime error naming the key
if has(ages, "dee") { ... }
let d: Int = get(ages, "dee", 0);          // read with a default
remove(ages, "bob");                       // no-op if absent
let n: Int = length(ages);

loop k in ages {                           // keys, insertion order
    fx { println(k, "=", ages[k]); }
}
let ks: Text[] = keys(ages);               // insertion order
let vs: Int[] = values(ages);              // same order as keys
```

Typing:
- The key type is `Text` in this release. `Int` keys follow only if measured demand appears; the design
  leaves room for them.
- `T` is any Aether type: `Int`, `Real`, `Bool`, `Text`, records, arrays and nested maps
  (`Map[Text, Int[]]`, `Map[Text, Map[Text, Int]]`).
- `m["k"]` has type `T`. `m["k"] = v` type-checks `v` against `T` (TYPE-001 on a mismatch, as for arrays).
- A literal's values must all be `T` (TYPE-001). Duplicate keys in a literal are a compile error.

Semantics:
- **Values, like arrays (D8 V-strict).** `let b = m` copies, and so does passing a map to a function. A
  function that changes a map returns it: `m = add_word(m, w)`. An un-returned write to a map parameter gets
  the same treatment as arrays under D8.
- **Iteration order is insertion order** (Python 3.7+ dict order). Re-assigning an existing key keeps its
  position; `remove` then a re-insert moves the key to the end.
- **Iterating while mutating** follows D18's foreach-snapshot rule: `loop k in m` iterates the keys as they
  were when the loop started.
- **Equality** follows D24 (structural): same key set and equal values, ignoring order.
- **Printing** a map (`println(m)`) prints `{"ann": 31, "bob": 27}` in insertion order, using D74's Real
  formatting for Real values.
- **Purity:** map operations are pure, and allowed in `@pure` functions.
- **TOON/JSON:** out of scope for this release. A `toon_to_map` / `map_to_toon` bridge is a natural follow-up.

## Diagnostics (new codes as needed, following the existing allocation rules)

- A missing key on `m["k"]` is a runtime error: `key "k" is not in the map; use has(m, "k") or get(m, "k",
  default)`.
- `{}` without a declared type: a compile error asking for `let x: Map[Text, T] = {};`.
- Python spellings get SCOPE-001 hints toward the function form, per D71 (no method calls on builtins):
  `dict`, `m.get(k)`, `m.keys()`, `m.items()`, `m.pop(k)`, `k in m`.
  - `k in m` as an expression: decide during implementation whether to accept it as sugar for `has(m, k)`.
    Accept only if it costs nothing elsewhere in the grammar; otherwise hint.
- A non-Text key in this release: TYPE-001 naming `Map[Text, T]`.

## Builtin names (D72)

`has`, `get`, `remove`, `keys`, `values` and `length` are short and generic.
- They are generic over the map's value type, so there is no per-type family.
- Engine registrations use Aether-private names (`aether_map_has`, …), never plain names: plain display
  names leak into every front end, as `count`/`sum` once broke Pascal.
- A user's own `fn get(...)` still wins over the builtin, as for every aliased builtin.

## Implementation plan

1. **Engine (pscal-core).**
   - An ordered hash map value with Text keys and boxed values.
   - Copy on assignment and on parameter passing, consistent with arrays.
   - Builtins under `aether_`-prefixed engine names.
   - Insertion order kept with a parallel key array or a linked list.
2. **Front end (aether).** The `Map[Text, T]` type in the type grammar and the type oracle; the literal and
   `{}`; index read and write; `loop k in m`; the builtins and their typing; the diagnostics above; structural
   `==`.
3. **Tests.** Fixtures for every operation and error, including nested maps, records as values, value
   semantics, insertion order and a missing key. Then the full surface registry, ctest and the
   instrument/replay check: archived programs never used maps, so expect no flips.
4. **Docs.** A spec section; full and medium guides (the medium guide stays under its o200k cap with paired
   cuts); D47's taught `Tally` idiom replaced by a map example; CHANGELOG; VERSION bump.
5. **Training data.**
   - Corpus programs whose parallel-array tallies read better as maps may be migrated, optionally.
   - New map-using instruction pairs, never from benchmark task text.
   - The corpus gate (`--check-gates`) must pass.
6. **Benchmark.** No existing task is changed. A future run measures whether models write maps correctly
   from the guide and the fine-tune.

## Out of scope

Sets (a `Map[Text, Bool]` serves until measured), non-Text keys, ordered-by-key iteration (sort `keys(m)`),
and a TOON/JSON bridge.
